# 06 --- 验证、兼容性与性能基线计划

## 1. 原则

COSBench
是基准测试工具。验证重点不仅是程序能启动，还包括请求是否等价、统计是否可信、分布式执行是否正确。

所有性能对比必须在相同硬件、网络、目标存储、对象大小、工作负载、并发模型、超时/重试和统计口径下进行。

## 2. 验证层级

### L1 --- 单元测试

覆盖： - workload 配置解析； - 参数默认值和边界校验； -
对象大小/名称生成； - 操作模型； - 统计计数和延迟聚合； -
错误分类和重试计数； - 配置合并规则。

### L2 --- 适配器契约测试

每个适配器都应验证： - 初始化和关闭； - 认证与 endpoint； - 基本操作； -
超时、失败和异常映射； - 返回值与统计字段； - 资源释放； - 特殊操作及
SineIO 扩展。

### L3 --- 集成测试

至少覆盖： - Controller 启动与 Driver 注册； - 提交工作负载； - Driver
执行； - 结果回传和聚合； - 任务失败和取消； - 重启、关闭与日志； -
发行包在干净环境中的启动。

### API 和运行时契约

迁移前先从源码和运行配置建立外部契约清单：HTTP method/path、请求与响应格式、错误状态、认证、端口、XML workload 输入和结果格式。至少覆盖 Driver 的 /i/*.command 路径及 Controller CLI 路径；以 golden request/response 或等价集成断言保护。不要仅以“服务启动成功”代替兼容性检查。

若用 Java SPI 替换 OSGi 服务发现，测试必须覆盖 factory 注册/排序、重复或冲突依赖版本、资源关闭，以及当前是否需要 Bundle 级类加载隔离。SPI 无法满足已确认的隔离要求时，不得据此宣称替换完成。

### L4 --- 端到端回归

选取代表性工作负载，与原版进行结果和行为对照。真实存储环境不可用时，使用可控的兼容服务测试协议行为，但不得把
mock 性能作为真实存储性能结论。

## 3. 必须固定的工作负载变量

每次基准记录： - COSBench 版本与 Git commit； - JDK 版本和 JVM 参数； -
CPU、内存、网卡、操作系统； - 目标存储版本、节点数和配置； -
网络拓扑和带宽； - 对象大小、数量、数据生成方式； - 操作类型和比例； -
worker/concurrency 数； - 执行时长、预热时长； - 连接池配置； -
timeout、retry、TLS； - 日志和监控开关； - 测试轮次及执行顺序。

## 4. 最小基准矩阵

| 场景 | 主要观察对象 |
|---|---|
| 小对象、高并发 PUT | 每请求固定开销、调度、签名和统计 |
| 小对象、高并发 GET | 连接复用、响应处理、延迟分布 |
| 大对象持续 PUT | 有效吞吐、缓冲区、网络和存储能力 |
| 大对象持续 GET | 流式读取、内存峰值、网络吞吐 |
| 混合读写 | 资源竞争和统计正确性 |
| 失败/超时场景 | 错误统计、重试、队列和资源释放 |
| 多 Driver 扩展 | 横向扩展、结果聚合、负载均衡 |

## 5. 统一统计定义

审计阶段必须从源码确认现有定义，之后再将定义写入测试规范。至少明确：

-   RPS 是发起数还是完成数；
-   逻辑操作和 HTTP 请求是否分别计数；
-   重试是否计入请求数；
-   吞吐量是否只统计有效 payload；
-   延迟计时从排队前、发起前还是发送前开始；
-   超时和失败如何进入延迟分布；
-   p50/p95/p99 的算法与采样方法；
-   多 Driver 数据如何合并；
-   预热阶段是否进入正式结果；
-   结果上报延迟是否影响 Driver 热路径。

不要在迁移时悄悄改变这些定义。如果有必要改进，应当明确标记为统计语义变更，并提供旧/新口径说明。

## 6. 资源与运行时指标

每次测试建议收集： - CPU 利用率； - RSS/常驻内存； - JVM heap； - GC
次数和总暂停时间； - 线程数； - 活跃连接和连接错误； - 文件描述符； -
网卡吞吐； - 请求队列深度； - RPS、有效吞吐、p50/p95/p99、失败率； -
Controller CPU/内存与 Driver CPU/内存。

## 7. 性能门槛

第一阶段只要求： - 无明显且无法解释的性能退化； -
同样操作语义下结果可比较； - 错误率和请求数据量符合预期； -
统计结果可重复。

具体阈值由基线测量后确定，不得先虚构"性能提升 20%"之类指标。
