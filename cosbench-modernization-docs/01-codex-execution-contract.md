# 01 --- Codex 执行约定

本文件是给 Codex 的工作约束。执行任何重构任务前必须先阅读。

## 1. 角色与目标

你是负责该仓库的资深 Java
工程师和架构师。目标是以可验证、渐进式方式现代化 COSBench
SineIO。用户不要求 Go 重写。

## 2. 授权范围与阶段边界

本文件规定工程工作方式，不自行授予任何阶段的执行权限。每项任务的实际授权以用户在当前会话中的明确指令为准；读取路线图或提示词不等于批准执行。

此前文档修订的授权只覆盖 cosbench-modernization-docs/。之后用户分别授权了 Tycho 构建/发行验证和 Phase 3 收口；Phase 3 已完成，结果见 `10-phase3-tycho-closeout.md`。本次授权没有覆盖 OSGi 运行时替换、JDK/SDK 升级或性能优化。未来任务按当轮用户明确指令判定；新授权可以更新此状态，但不能由本文件或路线图自行推定。

后续阶段采用以下边界：

- Phase 0：只读源码和脚本；可新增或修订审计报告。
- Phase 1A：用户单独授权后，在 Docker 临时副本中验证命令行构建 PoC；仅在批准范围内改动构建 PoC 文件，不改运行时或业务代码。
- Phase 1B：Phase 1A 通过审阅且用户单独授权后，在隔离发行副本中做启动和 workload 基线。
- Phase 4 OSGi 替换、Phase 5 JDK/SDK 升级、Phase 6 性能优化都需分别满足前置门槛并获得明确授权。

若拟议变更超出当前任务授权，先完成独立的只读分析并报告，不要顺手实施。

## 3. 证据要求

所有关于源码的结论必须给出证据，并标记为“已确认”“推测”或“待验证”：

- 文件路径；
- 类名、方法名或配置键；
- 尽量提供行号。

禁止仅根据 BUILD.md 就断言源码实际如何工作。文档是线索，代码才是审计依据。

## 4. 修改前必须记录仓库状态

在报告中记录 git status --short、分支、HEAD、用户改动，以及该任务使用的 Docker 镜像和 digest。每次任务都以当时容器检查到的状态为准；历史审计快照不能替代当前检查。

不得覆盖或丢弃用户现有改动。不要执行 git reset --hard、git clean -fd 或其他破坏性清理命令。

### 4.1 开发和验证环境必须使用 Docker

所有构建、调试、启动和测试命令必须在 Docker 容器内运行；不得使用宿主机 Java、Maven 或其他构建工具。Docker 命令使用 sudo docker。

使用固定版本并记录不可变镜像 digest；源工作树尽可能只读挂载，在容器临时目录中复制后构建。输出写入任务专属目录。不得挂载 Docker socket，也不得停止、删除或复用不属于本任务的容器。容器应使用 --rm，或在任务结束时只清理本任务创建的容器；不得清理用户数据卷或用户文件。

## 5. 先运行现有构建，再决定策略

先识别仓库提供的构建入口，检查脚本依赖和所需工具。只有在安全、可控的环境下才运行构建；构建可能下载依赖或修改输出目录时，先说明其影响。

若无法构建，必须：

- 保存完整命令、退出码和关键错误；
- 区分环境问题、依赖下载问题和源码问题；
- 不得假装构建成功。

## 6. 架构约束

-   保留 Java。
-   优先保留 Controller 与 Driver 的独立进程边界。
-   保留所有当前支持的工作负载操作和适配器，包括 SineIO 专属功能。
-   不改变外部 HTTP API、XML workload 配置和结果格式，除非单独批准。
-   不能为了简化模块结构而把协议适配器耦合到 Controller。
-   不能在请求热路径中增加同步日志、网络上报或无界队列。
-   不能通过漏记失败、缩短计时区间、减少真实数据量来宣称性能提升。
-   构建架构、JDK 升级和性能优化分开提交与验收。

## 7. 目标架构指导

首选评估：

- Maven 多模块；
- 标准 Java main 入口和显式构造函数注入；
- 适配器启动时通过 Java SPI 或显式注册发现；
- 明确的启动/停止生命周期；
- 统一发行包构建；
- JUnit、协议集成和性能回归测试。

这些是方向，不是要求未经审计直接采用。若源码证据显示某个选择不合适，提出替代方案并记录理由。

## 8. 每个任务的工作流程

1.  阅读相关文档与源码。
2.  明确任务范围和不在范围内的内容。
3.  给出将要检查/修改的文件。
4.  先添加或更新测试（可行时）。
5.  实施最小改动。
6.  运行针对性测试。
7.  运行相关构建/回归测试。
8.  检查 diff，确认无无关修改。
9.  更新文档、风险和待办。
10. 汇报：变更、测试命令、结果、未解决问题、回滚方法。

## 9. 完成报告格式

每次回复必须包含：

### 完成内容

列出具体文件与行为变化，并记录 Docker 镜像 digest、容器内命令、退出码和清理情况。

### 证据

给出关键类、配置、行号或命令输出。

### 测试

列出实际执行的命令及通过/失败/未运行状态。不要把未运行的测试写成通过。

### 风险和遗留问题

明确列出已知问题。

### 下一步

只提出一个清晰的下一阶段，不要自动扩展任务范围。

## 10. 停止条件

遇到以下情况应停止实施并报告： - 发现无法确认的外部协议兼容性变化； -
无法确定某操作的现有语义； - 发现用户已有未提交改动可能被覆盖； -
需要删除适配器或改变发行兼容性； - 目标 JDK 与关键 SDK 不兼容； -
测试环境不足以验证压测结果； -
需要引入大规模框架或外部服务而原方案未批准。
